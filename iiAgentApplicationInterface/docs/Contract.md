# iiAgentApplicationInterface 초기 계약

## 목적과 경계

응용 프로그램이 소유한 객체, 의미적 명령, 상태 변경을 같은 프로세스의 신뢰된 호스트가 등록한다. 소비자는 접근 가능한 객체와 기능만 발견하고, 입력 검증과 인가를 거쳐 호스트 명령을 실행한다. UI와 에이전트가 같은 명령을 사용하려면 앱이 두 경로를 이 런타임 또는 동일한 명령 구현에 직접 연결해야 한다.

C++ 모듈은 공통 기반 iiSDKCore와 JSON Schema 엔진에 의존하며 Qt, GUI 또는 모델은 요구하지 않는다. 앱이 필요한 모듈들을 조합한다. 빌드 시 선언 발견 도구는 소스와 컴파일 명령을 읽고 컴파일러와 libclang을 사용한다. 명령 계층은 앱이 명시한 프로세스와 스키마 리소스를 사용하고 Python 전송 계층은 호스트가 지정한 표준 입출력 또는 HTTP 엔드포인트를 사용한다. 인증 서비스나 샌드박스는 포함하지 않는다. 런타임의 등록·상태 게시 API와 콜백은 신뢰된 앱 코드에서만 사용한다. 외부에 직접 넘길 수 있는 보안 경계가 아니다.

## 객체와 기능

객체는 비어 있지 않은 고유 식별자와 타입, 설명 및 앱이 소유한 상태 문자열을 갖는다. 각 등록은 런타임 내에서 새로운 인스턴스 번호를 받고 초기 상태 리비전은 1이다. 같은 식별자를 제거 후 재등록해도 인스턴스 번호가 달라진다. 상태가 바뀌면 리비전이 증가하고 상태 변경 이벤트를 전송한다. 같은 상태의 재게시는 변경이 아니다. 조회는 객체별 읽기 인가에 통과한 항목만 반환한다.

명령 기능은 등록된 객체에 속하며 객체 안에서 고유한 식별자, 설명, 입력·출력 스키마 설명 문자열 및 권한 이름 목록을 갖는다. 기존 런타임은 이 문자열을 발견용 메타데이터로 취급하며 각 기능에는 앱이 제공하는 입력 검증기와 실행 핸들러가 반드시 필요하다. 별도의 `CommandSchemaValidator`는 명시적으로 제공된 JSON Schema를 검증하고 MCP 명령 서버는 입출력에 이를 적용한다. 객체 제거는 그 객체의 기능도 제거한다. 구체적인 버전과 한계는 [명령 계약](Commands.md)을 따른다.

## 인가와 실행

정책이 없거나 예외를 던지면 접근을 거부한다. 정책은 주체, 동작, 객체 식별자, 기능 식별자 및 기능 권한을 받는다. 객체 열람, 기능 발견, 실행 및 각 이벤트 전달에 대해 따로 판단한다. 기능 발견은 객체 열람도 허용되어야 한다. 명령은 실행 시 인가하고 입력 검증 및 등록 유지 확인 후 다시 인가한 뒤 앱 핸들러를 한 번 호출한다. 존재하지 않는 명령과 최초 인가가 거부된 명령은 모두 동일한 `denied: command unavailable` 결과를 반환한다. 실패한 인가나 검증은 핸들러를 호출하지 않는다. 실행 전 기능이 제거되거나 교체되면 호출을 거절한다. 검증기가 예외를 내면 검증 실패이고 핸들러 예외는 실행 실패이다.

호스트는 주체를 인증하고 권한을 결정해야 한다. 주체 문자열은 모듈이 인증하지 않는다. 권한 이름이나 스키마 설명 자체는 권한 검사나 검증을 수행하지 않는다. 인가·검증 콜백은 순수하게 판단하고 런타임을 재진입하지 않아야 한다. 핸들러가 같은 런타임에 상태를 게시하는 것은 허용한다. 핸들러 내부의 부작용, 취소, 원자성, 롤백, Undo/Redo 및 외부 승인 정책은 앱이 소유한다. 성공을 보고하기 전에 앱이 필요한 보장을 해야 한다.

## 상태 스트림과 수명

구독은 런타임과 동일한 스레드에서 동기적으로 이벤트를 받는다. 객체 생성·제거, 기능 등록·제거, 상태 변경과 허용된 명령 및 절차의 완료·실패를 알린다. 절차 이벤트는 객체 식별자 `application.procedure`, 기능 식별자에 절차 식별자, 인스턴스와 리비전에 0을 사용한다. 이벤트에는 종류, 객체 및 기능 식별자, 객체 인스턴스, 상태 리비전이 있으며 상태나 명령 결과는 담지 않는다. 각 이벤트마다 구독자의 현재 인가를 확인한다. 구독 해제 후에는 전달하지 않는다. 콜백 예외는 다른 구독자나 완료된 변경에 영향을 주지 않는다. 콜백에서 발생한 이벤트는 현재 이벤트의 전달이 끝난 후 순서대로 전달한다. 구독자는 구독 이전에 발생한 이벤트를 받지 않으며, 객체 제거에 따른 기능 제거와 객체 제거 이벤트는 한 묶음으로 먼저 예약된다.

모든 런타임 호출은 하나의 호스트 스레드에서 직렬화해야 하며 콜백은 동기 실행된다. 활성 호출이나 콜백 안에서 런타임을 파괴하지 않는다. 구독은 런타임 수명까지만 유효하고 별도 재생이나 지속성은 없다. 처음에는 구독한 뒤 스냅샷을 조회한다. 연결이나 이벤트 누락이 의심되면 읽기 인가를 거쳐 스냅샷을 다시 조회하고 인스턴스·리비전을 비교한다. 삭제된 객체의 이전 이벤트만으로 삭제 여부를 복원할 수 없으므로 전체 목록도 다시 조회한다.

## 언어와 배포

공개 C++23 API는 `<iiAgentApplicationInterface>`와 CMake 타깃 `iiAgentApplicationInterface::iiAgentApplicationInterface`로 제공한다. C ABI 헤더는 `<iiAgentApplicationInterface/AgentC.h>`로 사용한다. C ABI의 텍스트는 NUL을 포함하지 않는 UTF-8이며, 호스트 콜백이 반환한 포인터는 해당 외부 API 호출이 돌아올 때까지 유효해야 한다. C ABI가 반환한 출력은 `iiagent_application_interface_free`로 해제한다. Python 런타임 바인딩은 같은 네이티브 런타임의 C ABI를 사용하며 콜백을 런타임이 닫힐 때까지 보관한다. 명령 객체는 별도 네이티브 Python 확장으로 제공하고 전송 조정은 Python으로 구현한다. Python 바인딩은 공유 라이브러리가 필요하다. 빌드 옵션으로 테스트, 예제, Python 바인딩을 선택할 수 있다. 설치 스크립트는 명시적 경로 또는 `INSTALL_PREFIX`를 우선하며 그 외에는 `build/install`에 배치한다. C++ ABI 안정성과 기존 런타임의 멀티스레드 동시 접근은 보장하지 않는다.

## 빌드 시 선언 발견 계약

애플리케이션은 CMake 타깃에 빌드 발견 단계를 연결한다. 이 단계는 해당 타깃의 실제 컴파일 명령과 지정된 소스 범위를 libclang으로 분석하고, 타입·필드·메서드·변수 등 확인한 선언의 이름, 종류, 타입, 접근 수준, 소스 위치와 libclang이 인식한 문서 주석을 빌드 산출물에 기록한다. 앱은 `iiAgentApplicationInterface_enable_discovery(앱타깃 ROOTS 소스경로...)`를 로컬 라이브러리 연결 뒤에 한 번 설정한다. 생성된 `iiAgentApplicationInterface::generated::create_application_runtime(policy)`로 런타임을 만들면 카탈로그가 자동 게시된다. 이미 생성한 런타임에는 `publish_build_catalog(runtime)`을 한 번 호출할 수 있으며, 두 경로 모두 개별 선언을 수동 등록하지 않는다. 카탈로그 조회에도 기존 기본 거부 정책이 적용된다. 현재 카탈로그는 하나의 객체이므로 선언별·멤버별 인가는 제공하지 않는다. Python 호스트도 동일한 카탈로그를 같은 런타임 계약으로 게시할 수 있어야 한다.

컴파일 명령이 없거나 분석 오류가 발생하면 성공한 것처럼 빈 카탈로그를 만들지 않고 빌드 단계에서 오류를 보고한다. 이 단계의 결과는 소스 선언 목록이다. 런타임에 생성되는 실제 객체, 그 수명과 값, 사전 컴파일된 바이너리나 분석 범위 밖 선언이 모두 발견됐다는 뜻이 아니다. 선언의 발견은 멤버 호출 권한이나 호출 가능성도 부여하지 않는다. 실제 객체 연결과 타입별 호출은 별도 실행 계층의 책임이다.

빌드 발견에는 Python, libclang, 실제 컴파일러의 헤더 탐색 정보와 단일 구성 Ninja 또는 Makefiles의 `compile_commands.json`이 필요하다. 다중 구성 생성기는 서로 다른 설정의 선언을 섞지 않도록 현재 명시적으로 거부한다. libclang이 원본 컴파일러와 다르면 전처리·언어 해석이 완전히 같다고 보장하지 않는다. `IIAGENTAPPLICATIONINTERFACE_LIBCLANG`으로 libclang 경로를 지정할 수 있다. 일반적인 로컬 CMake 링크 타깃과 `LINK_ONLY`·`BUILD_INTERFACE` 연결을 따라가며 명시한 `ROOTS` 안의 선언을 수집한다. `ROOTS`를 생략하면 앱과 수집된 로컬 타깃의 소스 디렉터리 및 등록된 소스 파일의 디렉터리를 범위로 사용한다. 이미 빌드된 바이너리, 범위 밖 헤더, 해석하지 못한 조건부 링크 식, libclang이 노출하지 않는 선언, 실행 중 로드되는 코드와 구체화되지 않은 템플릿의 완전한 목록은 보장하지 않는다. libclang C API 자체도 Clang AST의 모든 정보를 제공하지 않는다고 [공식 헤더 문서](https://clang.llvm.org/doxygen/Index_8h_source.html)에 명시되어 있다. 각 선언은 등장한 컴파일 단위를 기록하고, 카탈로그의 `coverage`는 실제 값·호출·바이너리와 전체 앱의 완전성이 미지원임을 명시한다. 생성 단계는 빌드마다 검사하되 내용이 같으면 산출물을 다시 쓰지 않는다.

## 네이티브 절차와 실제 객체 계약

호스트는 기존 객체 식별자에 실제 C++ 객체의 약한 소유 참조와 정확한 정적 타입을 연결할 수 있다. 절차 실행자는 에이전트 주체와 절차 식별자에 대한 인가를 받은 뒤 호스트가 준비한 네이티브 함수를 호출한다. 절차에는 해당 주체로 객체·기능을 조회하고 기존 명령을 실행하는 컨텍스트가 전달된다. 컨텍스트는 별도의 네이티브 읽기 또는 쓰기 인가와 타입 확인을 통과한 객체만 실제 C++ 타입으로 제공한다. 약한 참조가 만료되거나 타입이 다르면 객체를 반환하지 않는다. 얻은 공유 참조는 사용하는 동안 객체의 수명을 유지한다. 객체 등록을 제거하면 이후 조회용 연결도 제거한다.

절차가 공개된 C++ 메서드나 객체 그래프를 직접 사용하는 경우 이를 기존 명령 버스에 자동으로 통과시키거나 트랜잭션·Undo·상태 이벤트를 보장하지 않는다. 이전에 얻은 포인터는 권한 철회로 회수할 수 없다. 네이티브 코드는 같은 프로세스의 권한으로 동작하므로 이 인터페이스 자체는 샌드박스가 아니며, 호스트는 실행할 코드의 출처와 전체 권한을 신뢰하고 인가해야 한다. 빌드 카탈로그 자체는 선언을 기술하며 실제 인스턴스 수명이나 절차 실행을 보장하지 않는다. 이들은 아래의 객체 생성 및 소스 절차 실행 경로가 담당한다.

C++ 절차는 앱의 실제 타입을 사용하는 `ProcedureContext::read_object<T>`와 `write_object<T>`를 제공받는다. 정확한 정적 타입, 런타임 객체의 읽기 권한과 네이티브 읽기·쓰기 권한을 각각 검사한다. 타입 확인과 C++ 객체 교환은 호스트와 절차의 컴파일러·표준 라이브러리 ABI가 호환된다는 전제에서만 동작한다. 절차 모듈은 `iiagent_application_procedure_v1` 심벌에서 버전이 있는 `NativeProcedureDescriptor`를 반환한다. 호스트가 선택한 로더는 실행이 끝날 때까지 모듈을 유지하고 런타임은 기술자의 크기·버전·식별자·진입점을 확인한 다음 권한을 검사한다. 기술자 버전은 C++ ABI 안정성을 보증하지 않는다. 자동 테스트는 macOS에서 별도 모듈 적재뿐 아니라 실행 중 소스 문자열을 컴파일·적재하고 실제 C++ 테스트 앱 객체를 변경하는 전 과정을 검증했다. 다른 플랫폼의 동작을 보증하지 않는다. Python 절차는 동일한 주체의 객체 스냅샷·기능 발견·명령 호출을 지원하지만 실제 C++ 객체를 타입이 있는 Python 객체로 직접 노출하지 않는다.

## 이름 변경

초기 로컬 시제품의 이름 `iiAgent`를 `iiAgentApplicationInterface`로 변경했다. CMake 패키지·타깃, C++ 헤더·네임스페이스, C ABI 심벌, Python 모듈과 설정 변수도 새 이름을 사용한다. 이전 이름의 호환 별칭은 제공하지 않으므로 기존 소비자는 호출과 빌드 설정을 바꾸고 다시 빌드해야 한다.

## 문서 투영

`src/sync_docs.py`는 루트의 README·AGENT와 이 계약을 읽어 원문 SHA-256, 줄 번호, 내용 및 제목을 가진 JSON 투영과 색인을 만든다. `--check`는 파일을 변경하지 않고 투영의 일치를 검사한다. 이 프로젝트 한정 투영의 형식은 `iiAgentApplicationInterface.document-projection.v1`이다. Workspace 공통 문서 도구가 제공되면 공통 형식과의 통합을 별도로 확인한다.



## 런타임 소스 절차와 자동 수명 추적 명세

런타임 소스 절차는 호스트가 제공한 컴파일·적재 백엔드를 통해 준비하며, 컴파일 전·적재 전·절차 실행 전에 각각 인가한다. 적재는 모듈 초기화 코드를 실행할 수 있으므로 적재 인가는 적재 호출 이전에 실시한다. 요청 식별자와 적재된 절차의 식별자가 다르거나 기술자가 호환되지 않으면 실행하지 않는다. 컴파일 및 적재 산출물은 실행이 끝날 때까지 유지한 후 백엔드의 수명 계약에 따라 해제한다.

C++ 호스트는 `SourceProcedureBackend`에 컴파일과 적재를 구현한다. 앱의 파일 저장소는 호스트가 이 포트에 조합한다. 컴파일러, 앱의 헤더·매크로·링크 설정과 ABI의 호환성은 호스트의 책임이다. C 호스트는 콜백 테이블로 같은 포트를 제공한다. Python의 `Runtime.execute_source`는 이를 호출하고 `iiagent_application_interface_native.NativeSourceBackend`는 호스트가 지정한 clang++ 스타일 컴파일러와 플래그를 사용하는 참조 백엔드이다. 앱이 제공한 저장소의 `create_artifact`, `open_diagnostics`, `remove_artifact`로 기존 `build/`의 실행 라이브러리와 임시 진단을 관리하며, 산출물 경로가 해당 디렉터리 바로 아래가 아니면 컴파일하지 않는다. `example/python_source_storage.py`는 앱이 iiFileProvider를 주입하는 어댑터이다. 소스는 셸을 거치지 않고 표준 입력으로 전달한다. 백엔드는 기본적으로 모듈을 유지하며 호스트가 명시적으로 `close()`를 호출할 때 해제한다. 즉시 적재 해제 옵션은 반환 이후 실행 코드, 콜백, 스레드, 함수 포인터 등 모듈에 대한 참조가 없다고 호스트가 보장할 때만 안전하다. 컴파일러가 성공을 보고해도 산출물이 없거나 비어 있으면 실패로 취급한다. 컴파일 실패나 인가 거부 후 사용하지 않는 산출물은 제거한다. 컴파일러 제한 시간은 직접 실행한 프로세스에 적용되며 그 자식 프로세스 전체의 종료까지 보장하지 않는다.

`Runtime::make_tracked_object<T>`로 생성한 공유 C++ 객체는 생성 직후 객체 레지스트리와 실제 객체 바인딩에 함께 나타난다. 마지막 공유 참조가 사라지면 객체를 먼저 소멸하고 등록과 명령을 제거하며 이벤트를 발행한다. 절차에서 얻은 공유 참조도 객체를 유지한다. 같은 식별자가 재사용되면 이전 객체의 소멸이 새 객체를 제거하지 않는다. 런타임이 먼저 파괴되어도 나중 객체 소멸이나 지연 콜백은 유효하지 않은 런타임을 참조하지 않는다.

마지막 참조가 소유 스레드에서 해제되면 제거 이벤트가 동기 전달된다. 다른 스레드에서 해제되면 제거를 안전한 큐에 넣으며, `set_lifecycle_dispatcher`로 설정한 호스트 디스패처가 소유 스레드에서 큐를 처리하도록 게시한다. 디스패처는 다른 스레드에서 호출될 수 있으며 호출과 게시된 작업을 안전하게 지원해야 한다. 디스패처가 없거나 작업을 잘못된 스레드에서 실행하면 소유 스레드에서 `drain_lifecycle()`을 호출할 때까지 레지스트리 항목이 남는다. 이미 실제 객체가 소멸했으므로 이 기간에는 약한 바인딩을 획득할 수 없다. 런타임의 일반 API와 콜백은 여전히 하나의 소유 스레드에서만 호출한다.

표준 C++의 선언 정보와 약한 참조만으로 임의 객체의 생성과 소멸을 모두 가로챌 수 없다. 따라서 이 구현은 `make_tracked_object<T>`로 만든 객체에만 자동 수명 추적을 제공한다. 기존에 생성된 객체, 스택 객체, 외부 모듈 객체 및 별도 생성 경로의 객체는 자동 등록되지 않으며 앱이 생성 경로를 통합하거나 명시적으로 연결해야 한다.

## 에이전트 절차 작성과 재사용 계약

에이전트는 현재 주체의 `procedure_authoring_context`에서 C++23 절차 계약, `ProcedureContext` 함수의 이름·서명·설명과 `Result`·`Status`·`Object`·`Capability`·`AgentContext`의 자료형 설명, 읽기가 허용된 객체별 상태·인스턴스·리비전·발견 가능한 명령을 함께 얻는다. 실제 객체에 대한 네이티브 읽기·쓰기 가능 표시는 해당 객체 바인딩의 생존 여부와 별도 네이티브 권한으로 각각 판단한다. 빌드 선언 카탈로그도 다른 객체와 동일하게 읽기 인가를 받은 경우에만 포함된다. 이것은 생성 시점의 스냅샷이며 이후 객체, 명령, 상태와 권한은 바뀔 수 있다. 선언 정보나 네이티브 접근 표시가 특정 C++ 멤버의 접근 가능성이나 C++ ABI 호환성을 보증하지 않는다. 객체의 `type`은 호스트 메타데이터이며 정확한 C++ 한정 타입명이나 헤더를 자동으로 보장하지 않는다. 빌드 카탈로그는 기존 계약대로 하나의 객체 단위로 인가하며 선언별 필터는 제공하지 않는다.

에이전트는 절차 식별자, 앱 헤더 등을 위한 프리앰블, 함수 본문을 직접 작성한다. `compose_procedure_source`는 `ProcedureContext& context`와 `std::string_view input`을 받는 C++23 함수 및 표준 모듈 기술자와 내보내기 심벌을 조립한다. 식별자를 소스 코드의 문자열 리터럴로 안전하게 변환하며 빈 식별자·빈 본문·내장 NUL은 거부한다. 프리앰블과 본문은 신뢰된 네이티브 소스이므로 작성자가 사용 가능한 선언과 헤더를 확인해야 한다.

`build_procedure`는 소스의 컴파일만 인가하고 수행한다. 성공한 절차는 컴파일 산출물을 보유하며 반복 실행할 수 있다. 각 실행은 적재와 실행을 다시 인가하고 기술자의 식별자·버전·진입점을 검사한다. 컴파일 산출물은 원래 백엔드에 종속되므로 백엔드는 산출물보다 오래 살아야 하고 같은 주소를 유지해야 하며, 다른 백엔드로 실행할 수 없다. 컴파일 권한이 철회된 뒤 이미 만들어진 산출물은 실행마다 적재·실행 권한이 있는 경우에만 사용할 수 있다. 빌드 및 실행 실패는 진단을 반환하며 컴파일된 절차를 파괴하면 산출물을 해제한다. 로드된 모듈의 장기 보존과 해제 안전성은 기존 백엔드 계약을 따른다.

C API는 작성 컨텍스트 JSON, 소스 조립, 컴파일된 절차 핸들과 반복 실행을 제공한다. Python API는 같은 C++ 런타임을 사용하고 콜백·백엔드와 핸들의 수명을 함께 유지한다. 실패한 일회성 호출과 컴파일 핸들 종료 후에는 콜백 참조 순환을 해제한다. `CompiledProcedure.execute`는 열린 런타임을 요구하고 `close`는 해당 핸들 자신의 활성 실행 중에 거부된다. 다른 핸들은 호스트 콜백에서 마지막 참조가 사라져도 해제된다. 런타임이 먼저 닫혀도 남은 컴파일 핸들은 닫아 산출물을 해제할 수 있다. C 호스트는 콜백과 사용자 데이터가 컴파일 핸들보다 오래 살도록 하고 활성 호출·콜백 중 핸들을 파괴하지 않아야 한다. 에이전트가 코드를 생성할 모델이나 에이전트 서비스는 포함하지 않는다. 앱이 인증된 에이전트에 이 계약을 전달하고 생성된 신뢰 코드를 제출한다.

## 외부 에이전트의 앱 내부 조작 계약

MCP와 별도로, 앱 프로세스가 소유한 하나의 `Runtime`에 외부 에이전트 요청을 연결한다. 외부 요청은 앱 소유 이벤트 루프에서 처리하며 소유 스레드가 아니면 거부한다. 모듈의 `ExternalGateway`는 전송과 인증 저장소에 의존하지 않으며, 앱이 제공한 인증 함수가 연결의 실제 전송 계층에서 얻은 피어 정보와 자격 증명을 검증한 뒤 반환하는 주체만 사용한다. 요청에 적힌 이름을 인증된 주체로 간주하지 않는다. 인증 함수가 없거나 거부하거나 예외를 발생시키면 요청을 거부하고, 인증은 요청마다 다시 수행한다. 인증과 각 명령·컴파일·적재·실행 권한은 별도이며 기본값은 거부이다.

외부 연결의 기본 발견 결과는 전체 앱 상태나 빌드 카탈로그를 포함하지 않는다. 객체 목록은 읽기 권한을 적용한 식별자·타입·설명·인스턴스·리비전만 페이지별로 반환하고, 상태와 명령은 에이전트가 특정 객체를 지정해 요청하며 명령 목록도 페이지별로 반환한다. 페이지 크기는 1~100이며 정렬된 식별자 커서는 연속 스냅샷을 보장하지 않는다. 객체 삭제·삽입에 따른 변경은 앱이 제공하는 이벤트 또는 별도 재조회로 확인한다. 명령 실행은 실제 앱 런타임의 `invoke`를 호출하고 입력 검증과 정책을 유지한다. 호스트가 소스 백엔드를 제공하면 에이전트가 전체 C++ 절차 소스를 제출해 동일한 런타임에서 실행할 수 있다. 이 호출은 동기식이므로 호스트는 컴파일 비용과 이벤트 루프 지연을 관리해야 한다.

표준 모듈은 iiNetwork와 iiJson을 직접 링크하지 않는다. 설치 패키지가 알려 주는 `iiAgentApplicationInterface_EXAMPLE_DIR`의 별도 호스트 어댑터는 앱에서 iiNetwork의 로컬 소켓과 iiJson을 조합해 한 줄 JSON 요청과 응답을 처리하며, 보조 Python 클라이언트와 CLI는 별도 프로세스에서 이 소켓에 연결한다. 자격 증명을 주체라고 취급하지 않고, 호스트 인증기가 토큰과 선택적으로 운영체제 피어 자격을 검증해야 한다. 데모 인증은 테스트에만 사용하며 자동 승인 저장소나 신뢰 정책을 제공하지 않는다. 실행 중인 앱에 어댑터를 연결하지 않으면 에이전트는 그 앱에 접근할 수 없다. 외부 이벤트 구독과 원격 컴파일 산출물의 지속 재사용은 이 초기 연결 범위에 포함되지 않는다.

외부 로컬 전송은 `iiagent.application.v1` 한 줄 JSON 요청과 한 줄 JSON 응답을 사용한다. `operation`은 `describe`, `list_objects`, `read_object`, `list_capabilities`, `invoke`, `execute_source`, `execute_draft` 중 하나이고, `describe`는 상태 본문 없이 사용 가능한 연산과 필수·선택 필드를 반환한다. 소스 실행이 활성화되면 앱 명령 호출 및 정확한 C++ 타입을 이용한 실제 객체 읽기·쓰기 인터페이스도 간략히 설명한다. 입력의 `credential`은 호스트 인증기로만 전달하고 응답에 넣지 않는다. 알 수 없는 필드나 `principal` 같은 주체 사칭 필드는 거부하며, 인증 후 필수 객체·명령 식별자가 없으면 잘못된 요청으로 반환한다. 응답 `status`는 C++ `Status`와 같으며 0이 성공이다. 기본 조회에서 상태 본문은 `read_object`로 지정한 객체에 한해 반환하며, 명령의 출력은 앱이 정한다. 이 상태는 앱이 게시한 스냅샷으로 실제 객체 메모리를 자동 직렬화하지 않는다. 앱이 변경을 게시하지 않으면 오래될 수 있다. 단일 객체 상태가 응답 크기 한도를 넘으면 반환하지 않으므로 세분화된 데이터가 필요하면 앱이 부분 조회 명령을 제공해야 한다. 한 연결은 한 요청만 처리하고 입력·출력 크기, 연결 수와 유휴 시간은 호스트가 제한한다. 응답을 받기 전에 클라이언트가 연결을 끊으면 해당 연결을 정리하며 다른 요청은 계속 처리한다. 끊긴 요청의 명령은 이미 실행됐을 수 있고 자동 중복 제거는 없으므로 재시도 안전성은 앱의 명령 계약에 달려 있다.

`ExternalClient`와 `python3 -m iiagent_application_interface_cli`는 실행 중인 앱의 소켓에 연결한다. CLI는 JSON 입력을 표준 입력에서 읽고 자격 증명은 앱이 제공한 환경 변수에서 읽는다. 운영체제 사용자 정보나 환경 변수 자체를 에이전트 승인으로 취급하지 않으며, 소켓 경로·서버 신뢰·비밀 저장과 전달 및 피어 확인은 앱과 호스트의 책임이다. 로컬 소켓 전송 자체는 암호화하지 않는다. macOS 테스트에서는 별도 앱 프로세스와 CLI 프로세스를 실제 로컬 소켓으로 연결해 부적격 호출 거부, 명령 실행, 네이티브 절차 컴파일·적재와 동일한 앱 객체의 상태 변경을 검증했다. 이는 Codex·Claude Code 세션이나 제품 앱 및 다른 운영체제의 검증이 아니다.
